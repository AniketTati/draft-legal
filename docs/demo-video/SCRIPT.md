# draftLegal — end-to-end explainer video

**Runtime:** 5 minutes 15 seconds — 3:36 of narration across 31 beats, plus the pauses where the
app is navigating. Those pauses are deliberate: each line waits until the screen it describes has
actually settled, so the picture can never lag the voice.
**Format:** screen recording + voiceover. No talking head, no music bed under the first line.
**Structure:** problem → the one thing nothing else does → the lifecycle in order → where it runs.

The spoken text lives in [`vo/`](./vo/) — one file per scene for reading, `full-narration.txt` for
the whole thing, and `vo/beats/` holding the per-line audio the video is actually cut against.
**None of it contains stage directions, markdown or symbols** — paste any of it into a voice engine
and get usable audio out. This document is the map from that audio to what is on screen.

---

## Why it is shaped this way

Three findings from how demo videos are actually made now, all of which changed the script:

1. **Lead with the pain, not the feature list.** The strongest SaaS explainers open on a problem
   the viewer already recognises, then show the product dissolving it. Scene 1 is 12 seconds of
   problem and names the product only at the end of it.
2. **Front-load the moment it clicks.** Every product has one moment where the value becomes
   obvious, and it has to land early. For draftLegal that is *asking the whole portfolio a
   question and getting a cited answer* — so it is scene 2, not scene 8.
3. **Under 90 seconds is the rule for an explainer; a tour is allowed to be longer.** You asked
   for end to end, so this is a five-minute tour. Scenes 1, 2 and 10 on their own cut to a
   ~1:40 version with no rewriting — that is the one to put at the top of the README.

## Numbers spoken aloud — verify these against your final recording

The script deliberately rounds, so ordinary drift in the demo data will not break the audio.
Only three numbers are spoken. Check each one is still true on screen before you record:

| Spoken | Screen right now | Breaks if |
|--------|------------------|-----------|
| "four hundred contracts … a hundred and forty six million dollars of executed value" (scene 9) | Analytics → **420** total, **USD 146.72M** | either moves materially |
| "around twenty six million dollars … next ninety days" (scene 8) | Renewals → **USD 26.10M ACV** | moves off ~26M |
| "two hundred thousand dollars for an eight week statement of work" (scene 2) | you type this into the assistant | — it is your input, always true |

Everything else — risk scores, the specific approval, counterparty names — is described
qualitatively, so you can re-record footage without re-recording audio.

One more line is tied to specific screen content: scene 6 says *"the liability cap sits far below
our floor for a vendor holding production data"*, which is the AI summary on the **Airtable — DATA
PROCESSING** approval. If that approval leaves the queue, the recorder warns and the line needs
changing. Nothing else in the narration names a counterparty.

## Text-to-speech notes

The narration is generated by [`tts.mjs`](../../scripts/demo-video/tts.mjs) using the Gemini API and
the key already in the repo-root `.env`. These rules are why the copy sounds right, and they apply
just as much if you paste it into any other engine:

- **No markdown, symbols, or abbreviations.** No `$`, `%`, `&`, `/`, `→`, no `e.g.`, no ALL CAPS
  (caps get spelled out letter by letter).
- **Money and large numbers are words** — "two hundred thousand dollars", not "$200K".
- **"Draft Legal" is two words on purpose.** Written `draftLegal` the engine says "draftle-gal".
  The audio should say it the way you say it out loud.
- **Short sentences.** Nothing over about 20 words, one idea each — that is what makes the
  prosody sound like a person rather than a paragraph.
- **No product jargon the engine will mangle** — pgvector, RRF, LangGraph and BYOK are all
  absent from the spoken text by design. They belong in the README, not the voiceover.
- **Paragraph breaks are pauses.** Keep them if you paste `full-narration.txt` in one shot.

**Voice:** currently **Charon**, which lands at 110–155 wpm across the beats — a measured demo pace.
`tts.mjs --sample` renders Charon, Kore, Algieba and Iapetus on the same line so you can compare.

**Delivery is set by instruction, not markup.** Gemini takes a plain-language note about manner
instead of SSML `<prosody>` tags. Keep any override about *manner only* — anything that reads as
content risks being spoken aloud. Check it by arithmetic: a 30-word line at ~14 seconds means the
instruction was not read; at ~35 seconds it was.

**One file per line, not per scene.** 31 short files is what makes per-line sync possible, and it
means a reworded line costs exactly one API call to regenerate.

## Putting it together

```bash
node scripts/demo-video/tts.mjs --voice Charon
node scripts/demo-video/record.mjs
node scripts/demo-video/mux.mjs
node scripts/demo-video/verify.mjs
```

`verify.mjs` writes `out/verify/index.md` — the frame from the middle of every line, next to that
line. Read it top to bottom to confirm each image already shows what its line says.

`tts.mjs` generates the narration straight from the files in `vo/` using the Gemini API and the
`GOOGLE_API_KEY` already in the repo-root `.env` — so the hand-off through an external
text-to-speech tool is optional now, not required. It writes `scene-NN-*.mp3` beside each script.
Run `--sample` first to audition voices.

The recorder reads the actual duration of each MP3 and holds each scene on screen for exactly
that long, so the audio and the picture stay locked without manual editing. Full details in
[`scripts/demo-video/README.md`](../../scripts/demo-video/README.md).
